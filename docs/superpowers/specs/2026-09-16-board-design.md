# 掲示板 初回実装設計

## 目的と確定範囲

学生・教師が学習内容や質問を投稿し、学生・教師が返信できる掲示板を、既存アプリのデザインで実装する。初回は投稿、返信、投稿へのいいね、教師投稿の固定お知らせ、投稿者の公開プロフィール、本人と教師による削除を扱う。通知、検索、カテゴリ、ハッシュタグ、問題カード、返信の階層化は対象外とする。

この設計は、承認済みの掲示板プレビューと現行のPrismaスキーマを優先する。添付の要件定義書・DB設計書は参考資料であり、旧案の投稿タイトル・カテゴリ・別のプロフィールテーブルは採用しない。プレビュー内の教師の称号・自己紹介はサンプルで、現行DBには教師用の称号・自己紹介カラムがない。

## 画面と権限

| 操作 | 学生 | 教師 |
| --- | --- | --- |
| 一覧・投稿詳細・公開プロフィールの閲覧 | 可 | 可 |
| 新規投稿 | 可 | 可 |
| 教師投稿の固定・解除 | 不可 | 可 |
| 返信・投稿へのいいね | 可 | 可 |
| 自分の投稿・返信の削除 | 可 | 可 |
| 他人の投稿・返信の削除 | 不可 | 可、履歴を記録 |

全操作に既存の `getCurrentUser()` を使い、非ログイン・無効化・論理削除済みのユーザーは利用できない。API側で役割と投稿者IDを照合し、クライアントから送られたユーザーIDを権限判定に使わない。

`/board` は「すべて」「自分の投稿」の2タブと本文入力欄を持つ。学生・教師とも投稿時は通常投稿となり、教師の投稿も作成直後には固定されない。教師は投稿後、その投稿のピン操作で固定・解除する。「すべて」では固定投稿を先頭にまとめ、固定内・通常内をそれぞれ新しい順にする。複数の固定投稿を許可する。「自分の投稿」と公開プロフィールの投稿一覧は固定状態に関係なく新しい順にする。1ページ20件ずつ読み込む。投稿本文または返信数を押すと `/board/posts/[postId]` で投稿単体、返信一覧、返信欄を表示する。タイムラインからの返信操作はX風の返信画面を開き、同じ返信データを表示する。投稿詳細の外側に「投稿詳細」という大見出しは置かない。

教師だけが教師作成の未削除投稿を投稿上のピン操作で固定・解除できる。固定投稿には「先生からのお知らせ」と固定マークを表示し、教師が自分または他の教師の投稿を固定・解除できる。学生作成の投稿は教師でも固定できない。固定・解除後は一覧の順序を再取得する。

投稿者の名前・アイコンから `/board/users/[userId]` を開く。公開情報は表示名、アイコン、学生の自己紹介・装備称号、投稿一覧のみとし、メールアドレス、学生番号、ポイント、学習成績を出さない。学生の自己紹介は既存の `student_profiles.bio` をそのまま読む。教師は表示名・アイコン・教師バッジと投稿数を表示し、存在しない自己紹介・称号を作らない。利用開始日や試験名の欄も置かない。

本文は投稿・返信とも空白のみ不可、最大280文字とする。改行は表示時に保ち、HTMLとして解釈しない。本文の長さはプレビューの `maxlength` と同じJavaScript文字列長でサーバーでも検査し、DBでは `char_length(body) <= 280` を追加の防御として使う。

## データモデル

既存の `users`、`roles`、`student_profiles`、`teacher_profiles`、`titles` を再利用する。新規テーブルは以下の4つだけとし、既存テーブルのカラムを変更しない。

| テーブル | カラムと制約 | 主な索引 |
| --- | --- | --- |
| `board_posts` | `id uuid PK`、`author_id uuid FK users.id NOT NULL`、`body text NOT NULL`、`is_pinned boolean NOT NULL DEFAULT false`、`created_at`、`updated_at`、`deleted_at NULL`。本文は空白のみ不可、280文字以下 | 「すべて」用 `(is_pinned DESC, created_at DESC, id DESC)`、投稿者一覧用 `(author_id, created_at DESC, id DESC)`。どちらも未削除行の部分索引 |
| `board_comments` | `id uuid PK`、`post_id uuid FK board_posts.id NOT NULL`、`author_id uuid FK users.id NOT NULL`、`body text NOT NULL`、`created_at`、`updated_at`、`deleted_at NULL`。本文制約は投稿と同じ | 未削除行の `(post_id, created_at, id)`、外部キー用の `author_id` |
| `board_post_likes` | `post_id uuid FK board_posts.id` と `user_id uuid FK users.id` の複合PK、`created_at` | 複合PKと外部キー用の `user_id` |
| `board_delete_logs` | `id uuid PK`、`target_type` は `post` または `comment`、`target_id uuid`、`deleted_by uuid FK users.id`、`reason NULL`、`deleted_at`。対象は異種テーブルなので `target_id` にFKを張らない | `(deleted_by, deleted_at DESC)`、`(target_type, target_id)` |

投稿・返信・削除ログのIDは既存モデルと同じUUID方式を使う。`created_at` と `updated_at` はタイムゾーン付き日時とする。投稿者・削除者への外部キーは物理削除を前提にせず、参照制限を使う。件数は最初から投稿テーブルへ複写せず、未削除の返信・いいねを集計する。

削除は `deleted_at` を埋める論理削除で、本文・返信・いいね・ログを物理削除しない。削除済み投稿は一覧とプロフィールに出さず、直接URLも404にする。投稿が削除されると返信といいねも表示・操作できない。返信単体の削除では、その返信のみ一覧から外す。教師が投稿または返信を削除した場合は、同じDBトランザクションで `board_delete_logs` に対象、教師ID、日時、任意の理由を1件記録する。本人削除は教師削除履歴に記録しない。

## APIとデータの流れ

| API | 内容 |
| --- | --- |
| `GET /api/board/posts?scope=all|mine&cursor=...` | 未削除投稿を20件取得。「すべて」は固定優先、「自分の投稿」は新着順。カーソルは「すべて」で `is_pinned`・`created_at`・`id`、他では `created_at`・`id` の組 |
| `POST /api/board/posts` | 学生・教師が本人として通常投稿。作成時の `is_pinned` は常に `false` で、ピン指定は受け付けない |
| `GET /api/board/posts/[postId]` | 投稿単体と未削除返信・件数を取得 |
| `PATCH /api/board/posts/[postId]/pin` | 教師が教師作成の未削除投稿を固定・解除。`isPinned` を真偽値で受け取る |
| `DELETE /api/board/posts/[postId]` | 本人または教師が論理削除。教師操作なら履歴も記録 |
| `POST /api/board/posts/[postId]/comments` | 学生・教師が返信。削除済み投稿は不可 |
| `DELETE /api/board/comments/[commentId]` | 本人または教師が返信を論理削除 |
| `POST /api/board/posts/[postId]/likes` | 未削除投稿に本人のいいねを作成。重複は増やさない |
| `DELETE /api/board/posts/[postId]/likes` | 本人のいいねを解除 |
| `GET /api/board/users/[userId]` | 公開情報と未削除の本人投稿を取得。投稿は同じカーソル方式 |

読み取り時は投稿者・装備称号・アイコンを関連テーブルから取得し、投稿ごとの個別DB問い合わせを避ける。件数と本人のいいね状態もまとめて取得する。新規投稿・返信・いいね・削除の直後は画面内の対象データを更新する。

入力不正は400、未ログインは401、権限不足は403、存在しない・削除済み対象は404を返す。投稿作成時のピン指定は400、学生によるピン操作や学生投稿へのピン操作は403にする。重複いいねは1件のまま成功扱いにし、解除済みいいねの再解除も成功扱いにする。並行削除では最初の1回だけ更新・教師ログ記録を行い、以後は404を返す。失敗した操作は画面に短い日本語メッセージを表示し、入力本文は保持する。

## DB変更の安全な進め方

Supabaseには既存のDB・データ・適用済みマイグレーションがある一方、このリポジトリにはローカルPrismaマイグレーション履歴がない。まずライブDBのテーブル・制約・マイグレーション履歴を再確認し、4テーブルの `CREATE TABLE`、外部キー、索引、本文制約、RLS設定だけを含む追加SQLをリポジトリへ保存する。同じSQLをSupabaseの追跡可能なマイグレーションとして適用し、適用記録と実テーブルを確認する。既存テーブルの `DROP`、`TRUNCATE`、データ更新、`prisma db push`、DBリセットは使わない。

新規テーブルは現行の公開スキーマと同様にRLSを有効化し、ブラウザーからの直接DB書き込みを許可しない。アクセスは既存のサーバー側Prisma接続とAPIの権限検査を経由する。適用前にアプリ接続ロールとRLSの整合を読み取りで確認し、SQLと適用先をレビューする。DB適用は設計書レビュー後に別途確認を得てから行う。アプリ接続には `DATABASE_URL` のTransaction mode、Prisma CLIには `DIRECT_URL` を使う。

DB適用後に `prisma/schema.prisma` の関係を追加してClientを生成する。Prismaが表現できない部分索引などはSQLマイグレーションを正本とし、PrismaからライブDBへの自動スキーマ同期は行わない。

## 検証基準

- 学生・教師の新規投稿はいずれも固定されない。教師が教師作成の投稿を後からピン操作した場合だけ固定・解除できる。学生は固定できず、学生投稿は教師でも固定できない。固定投稿は「すべて」の先頭に並ぶ。未ログイン・無効ユーザーは不可。
- 学生・教師は返信といいねができる。固定・解除後も「自分の投稿」と公開プロフィールは投稿日時順を保つ。
- 「すべて」「自分の投稿」、投稿詳細、X風返信画面、公開プロフィールが承認済みプレビューに沿う。検索・カテゴリ・ハッシュタグ・問題カードは存在しない。
- 投稿者名・アイコンから公開プロフィールへ移動でき、学生の自己紹介と装備称号はマイページと同じ値になる。非公開情報はレスポンスに含めない。
- 投稿・返信の280文字制限、空白判定、改行表示、削除済み対象の404、いいねの一意性を確認する。
- 本人は自分の投稿・返信のみ削除でき、教師は全件を削除できる。教師削除は履歴を残し、並行操作でも重複記録しない。
- ライブDBの既存テーブル、既存データ、既存マイグレーション履歴に削除・初期化が起きていないことを適用前後で確認する。
- 新しいパッケージを追加せず、型チェック、lint、関連する単一テスト、画面操作を検証する。
