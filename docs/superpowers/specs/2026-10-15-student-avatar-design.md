# 学生プロフィールアイコン：非公開アップロード設計

更新日: 2026-10-15。状態: 設計書承認済み。次は実装計画のレビュー。
この文書に基づいて実装計画を作成する。アプリ実装、依存関係の追加、Storage設定、本番反映はまだ開始しない。

## 1. 目的と対話で確定した仕様

学生が自分のプロフィール画像を変更し、マイページ・右上のユーザー表示・掲示板で同じ画像を利用できるようにする。

- 変更・削除できるのは、ログインした有効な学生本人だけ。
- 有効な学生・教師は、他の学生の現在の画像を閲覧できる。未ログインでは、画像URLを知っていても新規取得できない。
- 教師は既存の固定アイコンのまま。教師用の画像編集画面やマイページは作らない。
- 学生が画像を移動・拡大し、自分で切り抜く範囲を調整する。丸いプレビューで保存前に確認する。
- 元画像はJPEG・PNG・WebP、最大5MB。GIF・SVG・HEICは初回対象外。
- 保存するのは切り抜き済み512×512pxのWebP。画像の形自体は正方形で、画面では丸形に表示する。
- 画像本体は非公開のSupabase Storageへ、参照先は既存の `student_profiles.avatar_url` へ保存する。新規テーブル・カラムは追加しない。
- アップロードも画像取得もアプリのAPIを経由する。Storageの公開URL・閲覧用署名付きURLはブラウザーへ渡さない。
- 保存・DB更新が確定する前に、現在の画像を消さない。失敗・競合によって他の成功した更新を壊さない。

以下のAPI名、内部サイズ制限、競合検出、復旧手順は、この合意を実装可能にする具体化案として本書のレビュー対象に含める。

## 2. 既存コードとの関係

- `prisma/schema.prisma`: `StudentProfile.avatarUrl` が既に存在する。画像バイナリをDBへ格納しない。
- `src/lib/profile-data.ts`: マイページへ `avatarUrl` を返している。
- `src/app/profile/profile-dashboard.tsx`: 画像表示はあるが、画像編集・保存処理はない。名前・自己紹介・称号の編集とは独立した窓を追加する。
- `src/lib/board/read.ts` と `src/lib/board/contract.ts`: 投稿・返信・公開プロフィールへ学生の現在の `avatarUrl` を渡す経路がある。画像URLを投稿時点の固定スナップショットにはしない。
- `src/components/student-shell.tsx`: 右上は固定SVGで、現在は名前だけを解決している。画像データの受け渡しと更新への追従が必要。
- `src/app/api/me/route.ts`: 現在は画像を返していない。既存レスポンスを保ちつつ、自分の `profile.avatarUrl` を追加する。
- `src/lib/auth.ts`: `getCurrentUser()` にSupabase認証と開発用Cookie認証があり、有効状態を確認している。この認証を再利用し、新しいログイン方式は作らない。
- 現在の称号ショップの未コミット変更、問題データ、生成済みPrismaファイルは本機能と分離して保護する。

## 3. 採用方式と責務

採用するのは「ブラウザーで切り抜き → アプリAPIで検証 → 非公開Storageへ保存 → Prismaで参照先更新 → 認証付き画像APIで表示」の方式。
比較したもう一つの案はブラウザーからStorageへ直接アップロードする方式だが、今回は完了確認・一時ファイルの管理を別経路に増やさず、既存のアプリ認証で統一する。

- ブラウザー: 元画像の選択、向きの反映、移動・拡大、プレビュー、切り抜き済みWebPの生成。
- 変更API: 学生本人の認証、入力制限、画像の実デコードと再エンコード、Storage保存、競合を検出したDB更新。
- 画像API: リクエストごとの閲覧認証、現在の画像参照の照合、Storageからの非公開取得、キャッシュさせない画像応答。
- Storageアダプター: 固定バケット内のサーバー管理オブジェクトだけを扱う。DBへのアクセスはPrismaに限定する。
- 表示UI: 認証付きの同一オリジンURLを表示し、未設定・読込失敗では各画面の既存の初期アイコン／文字表示に戻す。

画像の閲覧者による保存・スクリーンショットや、既に端末へ取得された画像の消去までは保証しない。「未ログインで新しく取得できない」がアクセス制御の範囲である。

## 4. 編集画面

1. 学生のマイページに、画像の近くへ「アイコンを変更」を追加する。名前・自己紹介の変更とは別操作にする。
2. 画像を1枚選択する。拡張子だけでなく、対応形式・空ファイル・容量・画像として読めることを確認する。
3. 1:1の切り抜き領域と丸いプレビューを表示する。領域全体を画像が覆う最小倍率を基準に、1〜3倍まで拡大できる。
4. マウス／タッチで移動でき、キーボードでも位置・倍率を調整できる。画像外の空白が切り抜かれないよう移動範囲を制限する。
5. 「保存」で確定する。選択・調整だけではサーバーへ何も送信しない。「キャンセル」または編集時のEscapeで変更を破棄する。
6. 保存・削除の処理中は重複送信と窓の閉じる操作を無効にし、処理中表示を出す。処理終了後は適切な操作元へフォーカスを戻す。
7. 現在の画像がある場合は、削除確認後に初期表示へ戻せる。画像未設定時は削除を提供しない。
8. 窓はスマートフォンでも画面内に収まり、必要な部分だけスクロールする。エラーと保存・キャンセル操作が見えなくならないようにする。

プレビューと出力は同じ静止画を基にし、EXIFの向きを反映する。アニメーションは保存しない。編集用Object URLや画像バッファは、再選択・終了時に解放する。

## 5. 画像の制限と検証

- UIの5MBは `5 * 1024 * 1024` bytes（5MiB）とする。容量超過は読み込み前に説明する。
- 元画像は端末内だけで扱い、サーバーには切り抜き済みの静止WebPを1枚送る。元ファイル、元のファイル名、位置情報は保存しない。
- APIへ送るWebPは512×512px、最大2MiB。multipart全体は2MiBに64KiBの付帯情報枠を加えた量までとする。
- APIは認証後に実際の読込バイト数を制限する。`Content-Length`、拡張子、申告MIMEだけを信用せず、無制限に `formData()` へ渡さない。
- サーバーでWebPであること、512×512pxであること、1フレームの画像であることを確認して実デコードし、再度WebPへエンコードする。入力画素数・出力バイト数も制限する。
- 保存品質は85を基準とし、元画像の透明部分は維持する。EXIF・GPS等のメタデータは引き継がない。
- WebPを生成できないブラウザー、破損画像、偽装形式、空ファイルは説明付きで拒否する。形式を黙ってPNG等へ変更しない。

Vercel Functionsの本文上限は4.5MBのため、5MiBの元画像をそのままAPIへ送らない。この設計では、検証済みの小さな画像だけがアプリAPIを通る。[Vercel Functions Limits](https://vercel.com/docs/functions/limitations#request-body-size)

## 6. StorageとDBの表現

- 専用バケット名は `student-avatars`。テスト・本番は別Supabaseプロジェクト内に作り、いずれも非公開・WebPのみ・ファイル上限2MiBにする。
- オブジェクトキーは `<appUserId>/<version>.webp`。`appUserId` はアプリの `users.id`、`version` はサーバーが生成する新しいUUID。Supabase AuthのIDと取り違えない。
- DBへ保存する値は `/api/avatars/<appUserId>/<version>` という同一オリジンの相対URL。期限切れになる署名付きURLやStorage直リンクは保存しない。
- 画像APIは検証した2つのUUIDから固定バケットのキーを組み立てる。クライアントから任意のバケット、キー、外部URL、所有者IDを指定させない。
- 再アップロードで既存のキーを上書きしない。毎回異なるキーを使い、旧ファイルと新ファイルを混同しない。
- 削除はDBの `avatar_url` を `null` にして初期表示へ戻す。
- 導入前に既存の非null値を確認する。管理外の既存URLがあれば、その外部画像を新機能経由で表示・取得せず初期表示とする。再アップロードを促し、既存値を一括変更しない。
- 管理外の既存値も編集状態では元の値を `expectedAvatarUrl` として保持し、描画時だけ無効化する。表示用のnullとDBの元値を取り違え、再アップロードが常に競合する状態にしない。
- 管理外の外部画像はダウンロード・削除しない。過去から公開されていた外部画像自体を非公開にできるとは説明しない。

非公開バケットでは取得もアクセス制御対象となる。今回はブラウザー用のStorage読取ポリシーや署名付きURL配信を設けず、アプリサーバーに限定して取り扱う。[Supabase Storage Buckets](https://supabase.com/docs/guides/storage/buckets/fundamentals)

## 7. APIと権限

| API | 対象・入力 | 成功時 |
| --- | --- | --- |
| `POST /api/profile/avatar` | 有効な学生本人。multipartの `image` と、編集開始時点の `expectedAvatarUrl`（JSON表現の文字列またはnull） | `200 { avatarUrl: 相対URL }` |
| `DELETE /api/profile/avatar` | 有効な学生本人。JSONの `expectedAvatarUrl`（文字列またはnull） | `200 { avatarUrl: null }` |
| `GET /api/avatars/[userId]/[version]` | 有効な学生・教師。対象学生も有効で、DBに記録された現在の画像参照と一致する場合のみ | `200 image/webp` |

- 認証は既存の `getCurrentUser()` を使う。本人の判定にはサーバーで解決したアプリユーザーIDを使い、リクエストに指定された他人のIDは採用しない。
- 教師によるPOST・DELETEは403。未ログイン・無効アカウントは画像の取得も含め401。認証済みでも対象・現在参照・ファイルが存在しない場合は404。
- POST・DELETEは同一オリジンからだけ受け付ける。形式不正は400、容量超過は413、未対応の画像型は415、競合は409とし、UIへ安全な説明を返す。
- StorageやDBの障害・設定不足は適切な5xxで返す。内部例外・接続情報・キーをそのままUIへ渡さない。
- GET・HEADとも認証を通す。未認証での304応答やRange要求を、画像取得の抜け道にしない。
- 画像応答とそのエラー応答は `Cache-Control: private, no-store, max-age=0`、`Vary: Cookie` を付ける。画像には `X-Content-Type-Options: nosniff` を付ける。
- Storageへのリクエストや画像APIの応答を、Next.jsの共有キャッシュ、公開CDN、Service Worker等へ保存しない。画像APIはStorageへリダイレクトせず、画像本体を返す。
- 認証が必要な画像はブラウザーから同一オリジンへ直接取得する。Next.js画像最適化へ渡さない。`next/image` を使う場合も `unoptimized` を指定する。

Next.jsの既定の画像最適化は取得先へ認証ヘッダーを転送しない。インストール済み16.2.9の画像ガイドとRoute Handlersガイドを実装時にも確認し、静的化・共有キャッシュを有効にしない。

## 8. 保存・削除・競合の整合性

StorageとPostgreSQLを一つのDBトランザクションに入れられるとは扱わない。短いPrismaトランザクションと補償削除で、現在の画像参照を守る。

### 保存

1. 認証、画像検証、`expectedAvatarUrl` の確認を行う。
2. 新しい一意なキーへ画像を保存する。ここでは旧画像もDB参照も変更しない。
3. Prismaで有効な学生本人であることを再確認し、現在の `avatar_url` が `expectedAvatarUrl` と一致する場合だけ、新参照へ条件付き更新する。Storage通信中にDBロックを保持しない。
4. 競合・確定したDB失敗なら今回の新画像だけを補償削除する。成功した他の処理の画像へ操作を広げない。
5. DB確定後、旧参照がこの機能の同一所有者の管理キーであり、現在参照ではないことを確認してから旧画像を削除する。

### 削除

1. 認証と期待値の確認後、Prismaで同じ競合制御を使って参照をnullにする。
2. DB確定後だけ、元の管理画像の削除を試みる。既にnullなら成功として扱い、新しい別画像が入っていれば409にする。
3. 参照をnullへ変更する前にStorageだけを消して、DBに壊れた参照を残す順序にはしない。

すべての画像更新経路は同じ条件付き更新を通り、古い画像のキーを再び現在値へ戻すAPIは作らない。競合検出の基準は現在参照の一致であり、nullから変更・削除を経てnullに戻った履歴までは検出しない。一般の名前・自己紹介更新APIには任意の `avatarUrl` を受け付けさせない。

### 結果不明と後片付け

- Storage保存やDBのcommit結果が不明な例外では、失敗したと決めつけて新画像を消さない。直後のDB読取で古い値が見えても、処理中のcommitが後から確定する可能性があるため即時削除せず、後述の保留ファイルの後片付けへ回す。
- UIでも応答を失った場合は現在のプロフィールを読み直す。未確定なのに成功を表示したり、古い参照へ強制的に巻き戻したりしない。
- DB確定後の旧画像削除だけが失敗した場合、プロフィール更新は成功のままにし、秘密情報を含まない後片付けログを残す。更新全体の失敗として再送を誘発しない。
- サーバー強制終了等では未参照ファイルが残る可能性がある。初回には定期実行・新規管理テーブルを作らず、未参照候補を一覧する読取専用手順と、確認後の削除手順を運用資料へ用意する。
- 後片付けは専用バケットの正規のキーだけを対象とし、作成から24時間以上経過したものに限定する。所有者のプロフィール行のロックを短いDBトランザクションで取得して進行中の更新確定を待ち、現在参照と再照合する。未参照が確定したキーだけを、ロック解除後にStorageから削除する。既存キーを再採用しない規則と併せて誤削除を防ぐ。
- 行ロックを取得できない、照合できない、所有者を確認できない場合は削除を保留する。実削除には別途確認を取り、一括削除やフォルダー全消去をしない。

## 9. 表示への反映と既存機能の保護

- マイページ、全学生画面の右上、掲示板の投稿・返信・他人から見たプロフィールで同じ現在参照を利用する。掲示板の自分の投稿・返信入力欄でも、アイコンがある箇所は同じ扱いにする。
- 自分の画面は保存・削除成功後に画像参照を更新する。他の利用者は次回取得・画面再表示時に反映される。リアルタイム配信は追加しない。
- 右上は `userName` が既に渡されている画面でも画像を解決できるようにし、不要な重複API呼出しやポーリングを追加しない。
- `/api/me` の既存フィールドは削除せず、自分の画像参照を追加する。認証状態・ポイント・名前の解決を壊さない。
- 編集が失敗・キャンセルされた場合、確定済みプロフィールや称号を変更しない。名前変更称号の判定・ポイント・通知を画像更新では発火させない。
- 画像取得エラーでは同じURLを無限再試行せず、初期表示へ戻す。次の画像バージョンでは正常に再読込できるようにする。
- 教師の固定表示、教師ホーム・学習状況画面の独立した表示設計、未実装のランキングには機能を広げない。

## 10. 設定・依存関係・環境分離

- サーバー専用Storageクライアントを設け、既存の認証用クライアントとは分ける。認証用Cookieやユーザーセッションを管理用クライアントへ持ち込まない。
- URLはその環境の `NEXT_PUBLIC_SUPABASE_URL`、キーはサーバー専用の `SUPABASE_SECRET_KEY`（未指定なら同環境の `SUPABASE_SERVICE_ROLE_KEY`）を使う方針とする。公開キーで管理処理へフォールバックしない。
- 特権キーは `NEXT_PUBLIC_` の変数、クライアントバンドル、APIレスポンス、ログ、Gitへ出さない。未設定なら画像機能を安全なエラーで停止し、他機能や既存の初期アイコンは維持する。
- バケットを実行時に自動作成・公開化しない。導入時にバケット設定と既存Storageポリシーを確認し、対象バケットへの匿名・通常JWTによる直接取得／一覧／変更を拒否する。広い既存ポリシーがあっても拒否できる、新バケット限定の設定にする。
- StorageクライアントのサービスキーはRLSを迂回するため、本人・閲覧者・固定キーの検査を必ずアプリAPI側で行う。他バケットや既存ポリシー全体を不用意に変更しない。
- サーバーの実デコード・再エンコードには `sharp` を採用する方針。現在はNext経由で0.34.5が入っているが、アプリの直接依存ではない。依存追加・バージョン固定は実装計画で提示し、承認前に実行しない。
- 切り抜きUIは初回の移動・倍率・1:1の範囲に絞る。回転・フィルター・複数画像等の編集機能は追加しない。
- `scripts/test-environment.mjs` は現在すべての管理キーを空にしている。専用テスト設定に明示されたテスト用キーだけを渡す拡張が必要で、通常環境や本番キーを拾わせない。
- 専用テストプロジェクトは既存の `grzylombpqmidltnbwhx`。DB接続先だけでなくStorageのURLも検証する。テストキー不足なら実Storageテストを停止し、成功したとは報告しない。
- 開発用test-studentログインはSupabaseのJWTを作らないが、APIが既存の開発用認証を使うためこの方式で検証できる。本番ビルドでは開発用認証が無効であることと、実Supabaseログインの経路も別に確認する。

## 11. 検証・受入条件

実装前に判定・副作用のテストを失敗させ、実装後に成功へ変わることを確認する。画像・Storageの成功だけで機能全体の成功とはみなさない。

- JPEG・PNG・WebP、縦長・横長・小さい画像、透明画像、向き情報付き画像で、プレビューと保存後の切り抜きが一致する。
- 5MiBの元画像境界、空・破損・形式偽装、未対応形式、2MiBの送信境界、512px以外・複数フレームのAPI入力を確認する。
- 位置調整・拡大・再選択・キャンセル・削除確認・キーボード・タッチ・二重クリックとObject URLの解放を確認する。
- 学生Aの保存画像を学生B・教師が閲覧できる一方、B・教師はAを変更できないことを、UIだけでなくAPI入力の偽装でも確認する。
- Cookieなし・ログアウト後・無効アカウント・他roleで画像を取得できないこと、HEAD・条件付き要求・Rangeや直Storage URLでも抜け道がないことを確認する。
- レスポンスヘッダーと実ネットワーク要求を調べ、画像の公開URL・署名付きURL・特権キー・画像最適化キャッシュへの流出がないことを確認する。
- 保存競合、保存と削除の競合、編集開始後の別タブ更新を発生させ、409と現在参照の保持を確認する。
- Storage失敗、DBの確定した失敗、commit結果不明、旧画像の削除失敗を分けて注入し、正常な画像を誤削除しないことを確認する。
- 名前・自己紹介・称号・ポイント・通知・掲示板投稿は変えず、画像だけが更新されることを確認する。
- 専用テストDB／Storageで実保存・差替え・削除を確認する。疑似応答によるUIテストと、実Storage連携テストの結果を区別して報告する。
- PCとスマートフォン幅で、ページの同一性、空白画面・フレームワークエラー・コンソールエラー・横はみ出し、操作とフォーカス復帰を確認し、リポジトリ外にスクリーンショットを保存する。
- 既存の全テスト、追加テスト、`npm run lint`、`npm run typecheck`、`npm run build` を実行し、失敗・スキップ・既存警告を区別して報告する。

## 12. 導入・復旧・対象外

設計書の承認後に実装計画を提示し、その承認後にテスト環境から着手する。依存関係追加、テストStorage設定、本番環境変数・Storage設定、pushはそれぞれ必要な確認を取る。
本番Storageの実設定・残高・利用量・既存データは、この設計書作成では操作していない。実装開始時の接続先・設定確認を導入条件とする。

本番反映前にDBと現在参照される画像ファイルを別々にバックアップする。DBバックアップだけではStorageの画像本体は復元できないため、画像ファイルとオブジェクトキーの対応も退避する。[Supabase Database Backups](https://supabase.com/docs/guides/platform/backups)
更新後に旧画像を物理削除すると、DBの値だけを戻しても旧画像は復元できない。復旧には対応する画像バックアップが必要である。
アプリのロールバックだけで旧バージョンの全画面へ新画像が表示できるとは保証しない。新しい画像APIがなくなる場合は初期表示へ退避し、復旧手順に従う。公開バケット化を復旧策にはしない。

対象外は、教師の画像編集、Google画像の自動同期、公開プロフィールサイト、画像編集の回転・加工、画像履歴画面、画像のリアルタイム同期、自動の定期清掃、本番DBの一括画像移行。

## 13. 自己レビュー

- 対話の確定事項と具体化案を区別し、非公開と署名付きURL配信を混同していない。
- 既存の `avatar_url` に認証付き相対URLを保存するため、Schemaの追加なしで既存の表示経路へ接続できる。
- 5MiBの元画像とAPIへ送る2MiB以下の画像を区別し、Vercelの本文上限と矛盾しない。
- StorageとDBの非原子的な境界、競合、commit結果不明、後片付け失敗、バックアップ範囲を記載した。
- 実装計画の承認やパッケージ追加の承認を、設計書作成の承認で代用しない。
