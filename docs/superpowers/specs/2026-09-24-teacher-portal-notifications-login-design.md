# 教師ポータル・通知・ログイン再設計

## 目的と確定範囲

共通教師アカウントで利用する教師ポータルを追加し、教師が学生の学習状況を確認しながら既存掲示板を管理できるようにする。同時に、学生・教師に共通する通知基盤と、承認済みプレビューに沿った学生・教師ログイン画面を実装する。

今回の実装範囲は次のとおりとする。

- 教師の共通アカウントによるログインと、開発環境専用の `test-teacher`
- 教師ホーム、学生一覧、学生別学習状況、掲示板、通知、ログアウト
- 教師による通常投稿、教師投稿のピン固定・解除、全投稿・返信の削除
- 掲示板で自分の投稿に返信されたときの個別通知
- 教師が投稿を初めてピン固定したときの全学生向け通知
- 学生・教師共通の通知一覧、個別既読、ベルの未読件数
- 学生・教師ログイン画面の共通デザインへの更新

称号獲得通知は、将来の称号条件機能から利用できるデータモデルだけを用意する。今回の実装では称号条件判定と称号獲得通知の発行は行わない。模擬試験管理、問題登録、月間ランキング管理も今回の対象外とする。

## 現状と前提

- `users`、`roles`、`student_profiles`、`teacher_profiles` は既に存在する。
- `board_posts`、`board_comments`、`board_post_likes`、`board_delete_logs` と掲示板API・画面は実装済みである。
- 学生と教師は掲示板へ通常投稿と返信ができ、教師は教師投稿だけを後からピン固定できる。教師は全投稿・返信を論理削除できる。
- 教師ログイン画面は現在、開発用学生ログインAPIへ接続された仮実装である。
- `StudentShell` のベルには固定サンプルが表示されるが、通知テーブルと通知APIは存在しない。
- 学生の学習詳細集計は `getStudentLearningData()` にあり、教師向け画面では同じ集計規則を再利用できる。

既存のSupabase DB、既存データ、適用済みマイグレーションは削除・初期化しない。アプリ実行はTransaction modeの `DATABASE_URL`、Prisma CLIは `DIRECT_URL` を使用する。

## 認証と役割

### 本番の教師ログイン

教師ログインはSupabase Authのメールアドレス・パスワード認証を使う。共有教師アカウントは事前にSupabase Authへ作成し、同じメールアドレスの `users` 行を `teacher` ロール、表示名 `管理者` として用意する。認証情報やサービスロールキーはリポジトリへ保存しない。

ログイン成功後はアプリユーザーを読み込み、`teacher` ロールなら `/teacher` へ遷移する。教師として事前登録されていないアカウントは教師画面へ入れず、セッションを終了して日本語エラーを表示する。既存の `ensureAppUser()` はメールアドレスで見つかった教師のロールを維持し、新規Google利用者だけを学生として作成する。

### 開発用教師ログイン

開発環境だけで `/api/dev/test-teacher-login` を有効にする。入力アカウントが `test-teacher` の場合、`test-teacher@test.local` の教師ユーザーと `teacher_profiles` を安全にupsertし、表示名を `管理者` に固定して開発用Cookieを発行する。本番では404を返す。

### 役割別遷移

- 未ログイン利用者は保護画面から `/login` へ移動する。
- 学生が `/teacher/**` を開いた場合は学生ホーム `/` へ移動する。
- 教師が学生ホーム `/` を開いた場合は `/teacher` へ移動する。
- 教師にはマイページ、名前変更、自己紹介変更、称号を提供しない。
- 教師の公開表示名は常に `管理者` とし、掲示板・通知・教師シェルで紫系の文字色、太字、教師バッジを使って学生名と区別する。

## 画面構成

### ログイン画面

学生 `/login` と教師 `/login/teacher` は同じコンポーネント構成を使う。

- デスクトップは左30%、右70%の左右分割とする。
- 左側は濃紺のブランド領域で、トロフィーと「目指せ合格！過去問くん」の画像ロゴを表示する。キャラクターは使用しない。
- 教師側は「学びを支える 教師用ポータル」、学生側は「今日の一問から、合格へ一歩ずつ。」を表示する。
- 右側は教師ならアカウント・パスワード・ログイン、学生ならGoogleログインを表示する。
- 入力欄、ログインボタン、学生・教師画面の切替リンクは同じ左端と同じ最大幅に揃える。
- 教師画面に「管理者専用」ラベルは置かない。
- スマートフォンではブランド領域とフォームを上下に積み、操作領域を先に読める高さへ圧縮する。

### 教師シェル

教師専用 `TeacherShell` を追加し、既存アプリの濃紺サイドバーと青いアクセントを継承する。メニューは「教師ホーム」「学習状況」「掲示板」「通知」「ログアウト」のみとし、マイページ、称号、学生向け学習メニューは表示しない。ヘッダーには紫系の教師アバター、固定名 `管理者`、ベルと未読件数を表示する。

### 教師ホーム `/teacher`

承認済みの操作優先型B案を採用する。

- 上部に「今日の管理を始めましょう」の案内と「学生の学習状況を見る」「掲示板に投稿する」の2ボタンを置く。
- その下に学生の最新状況を、表示名、最終学習、回答数、正答率の表で表示する。
- 「＋ 掲示板に投稿」と「未読通知 ○件」の独立クイックカードは置かない。
- 登録学生数、今月学習した学生数、今週の回答数、固定中のお知らせ数は小さな状況表示として使えるが、主操作より目立たせない。

### 学習状況 `/teacher/students`

承認済みの一覧A案を採用する。アクティブな学生だけを表示し、表示名、最終学習日時、総回答数、総正解数、正答率を確認できる。表示名から `/teacher/students/[userId]` を開く。初回は新着学習順のページ分割一覧とし、複雑な検索やCSV出力は追加しない。

学生詳細は基本情報と集計カードに続き、「過去問練習」「一日一問」の2タブを置く。

- 過去問練習: 完了日時、試験、問題数、正解数、正答率、獲得ポイント
- 一日一問: 回答日、問題、選択肢、正誤

教師は閲覧だけを行い、学生の名前、自己紹介、ポイント、回答記録を変更できない。

### 掲示板

掲示板のURLとAPIは学生・教師で共有する。教師が `/board`、投稿詳細、公開プロフィールを開いた場合は `TeacherShell`、学生の場合は `StudentShell` で包む。

教師の新規投稿は常に通常投稿として作成され、作成直後は上部固定しない。教師が投稿上のピン操作を行った場合だけ固定し、「先生からのお知らせ」を表示する。固定対象は教師投稿だけで、学生投稿は教師でも固定できない。既存の本人削除と教師による全件削除、教師削除履歴は維持する。

## 通知設計

### 通知種別

| 種別 | 宛先 | 発行条件 | 移動先 |
| --- | --- | --- | --- |
| `board_reply` | 元投稿の作成者 | 別の利用者が未削除投稿へ返信したとき | 返信先の投稿詳細 |
| `board_pinned` | 全アクティブ学生 | 教師投稿が初めて `false` から `true` へ固定されたとき | 固定された投稿詳細 |
| `title_unlocked` | 対象学生 | 将来、称号条件を達成したとき | 将来の称号画面 |

投稿者本人が自分の投稿へ返信した場合は `board_reply` を発行しない。返信通知は返信1件につき1回とする。固定通知は同じ投稿を解除して再固定しても、各学生へ通算1回だけとする。教師同士には固定通知を配信しない。

### データモデル

新規テーブル `notifications` を1つ追加する。

| カラム | 内容 |
| --- | --- |
| `id uuid PK` | `gen_random_uuid()` |
| `recipient_id uuid NOT NULL` | `users.id`、削除制限 |
| `actor_id uuid NULL` | 返信者または固定操作教師の `users.id`、削除制限 |
| `type varchar(30) NOT NULL` | `board_reply`、`board_pinned`、`title_unlocked` のチェック制約 |
| `board_post_id uuid NULL` | 固定通知の対象投稿 |
| `board_comment_id uuid NULL` | 返信通知の発生元返信 |
| `title_id uuid NULL` | 将来の称号獲得通知 |
| `read_at timestamptz(3) NULL` | 個別既読日時 |
| `created_at timestamptz(3) NOT NULL` | 作成日時 |

通知種別ごとに必要な参照が1つだけ入るチェック制約を追加する。重複防止は次の一意制約でDBにも保証させる。

- `(recipient_id, type, board_comment_id)`
- `(recipient_id, type, board_post_id)`
- `(recipient_id, type, title_id)`

PostgreSQLではNULLを含む一意制約が他種別を妨げないため、返信、固定、称号を独立して重複防止できる。外部キー列には索引を置く。通知一覧と未読件数向けに `(recipient_id, created_at DESC, id DESC)` と、`read_at IS NULL` の部分索引 `(recipient_id, created_at DESC)` を置く。

テーブルはRLSを有効化し、ブラウザーからの直接書き込みを許可しない。通知の読み書きはサーバー側Prismaと、認証済み本人を確認するRoute Handlerだけを通す。

### 発行トランザクション

返信作成は、`board_comments` の作成と `board_reply` 通知の作成を同じDBトランザクションで行う。対象投稿が削除済み、返信者と投稿者が同一、投稿者が無効または削除済みの場合は通知を作らない。

ピン固定は、投稿の固定状態更新と学生向け `board_pinned` 通知の一括作成を同じトランザクションで行う。`false` から `true` へ変わるときだけ候補を作り、アクティブかつ未削除の学生IDを取得して `createMany(..., skipDuplicates: true)` でまとめて挿入する。一意制約により、解除後の再固定や並行操作でも重複しない。

### 通知APIと画面

| API | 内容 |
| --- | --- |
| `GET /api/notifications?cursor=...` | 本人の通知を新しい順に20件取得し、次カーソルと未読件数を返す |
| `GET /api/notifications/unread-count` | 本人の未読件数だけを返す |
| `PATCH /api/notifications/[notificationId]/read` | 本人の通知1件だけを既読にする。再実行も成功扱い |

`/notifications` は承認済みのB案で、新しい順の1列一覧とする。未読行は淡い青背景と未読ドットで区別するが、返信を示す「返」アイコンは置かない。通知を押すとその1件を既読にして対象投稿へ移動する。「すべて既読にする」は置かない。対象投稿が削除済みの場合は既読化したうえで、移動できない旨を一覧内に表示する。

## 教師向けデータ取得

教師ホームと学生一覧は専用の読み取りサービスへ分離し、ページから直接複雑なPrismaクエリを書かない。

- `getTeacherDashboardData()` はアクティブ学生数、当月に回答した学生数、今週の回答数、固定中の教師投稿数、最近学習した学生を返す。
- `listStudentLearningSummaries()` はページ単位で学生と集計値を返す。学生ごとの個別問い合わせを避け、`groupBy` とまとめた関連取得を使う。
- `getTeacherStudentDetail()` は学生基本情報、総合集計、過去問練習履歴、一日一問履歴を返す。

日時境界は既存機能と同じAsia/Tokyo基準を使う。正答率は回答数0件なら0%とし、それ以外は `correct / answer * 100` を整数へ丸める。教師用API・Server Componentは必ず `teacher` ロールを再確認する。

## エラー処理

- 未ログインは401またはログイン画面へ遷移、教師権限不足は403または学生ホームへ遷移する。
- 教師ログイン失敗は資格情報の誤りと教師権限不足を区別した短い日本語メッセージにする。
- 通知ID不正は400、本人以外の通知は404として存在を漏らさない。
- 通知発行に失敗した場合は元の返信・ピン変更もロールバックし、通知と掲示板状態を不整合にしない。
- UI操作の失敗時は画面内容を保持し、再試行できる日本語メッセージを表示する。

## DB変更の安全な進め方

通知テーブル、外部キー、制約、索引、RLSだけを含む追加SQLを新しいSupabaseマイグレーションとして保存する。既存テーブルへの破壊的変更、既存データ更新、`DROP`、`TRUNCATE`、`prisma db push`、DBリセットは行わない。

実DBへ適用する前に、接続先、既存テーブル、適用済みマイグレーション、SQL全文を再確認し、ユーザーの明示承認を得る。適用後は通知テーブル、制約、索引、RLS、既存テーブル・データ・履歴が維持されていることを読み取りで検証する。

教師アカウントの作成は通知マイグレーションに混ぜない。Supabase Authの共有教師アカウントとアプリ側教師ユーザーの準備は、認証情報を表示しない独立した手順として扱う。

## テストと受入基準

- 学生Googleログイン、教師メール・パスワードログイン、開発用 `test-teacher` がそれぞれ正しい画面へ移動する。
- 学生は教師URLへ入れず、教師は学生ホームへ入らない。教師にはマイページと称号が表示されない。
- 教師・学生ログインがキャラなし、左3:右7、入力欄・ボタン・切替リンクの左端揃えとなり、スマートフォンでも操作できる。
- 教師ホームから学習状況と掲示板へ移動でき、不要な2つのクイックカードがない。
- 学生一覧と学生詳細の集計が既存回答データと一致し、過去問練習と一日一問を切り替えられる。
- 教師の通常投稿は固定されず、教師がピンした場合だけ上部固定される。学生投稿はピンできない。
- 他人が自分の投稿へ返信すると1件通知され、自己返信では通知されない。返信作成と通知作成は同時に成功または失敗する。
- 教師投稿を初めてピンすると全アクティブ学生へ1件ずつ通知され、解除・再固定しても同じ学生へ追加されない。
- 通知は新しい順で、未読表示、個別既読、未読件数、投稿詳細への移動が動作する。「返」アイコンと一括既読操作がない。
- 教師の表示名は掲示板、教師シェル、通知で `管理者` に固定され、特別な色と太字で表示される。
- 未ログイン、権限不足、不正ID、削除済み投稿、並行したピン・既読操作を検証する。
- `node --test`、`npm run lint`、`npm run typecheck`、`npm run build`、`git diff --check` が成功する。
- 既存DB、既存データ、適用済みマイグレーションが削除・初期化されていない。
